**这版草图里藏着三个产品主张**：① 一个游戏可以有**多个可执行文件**（正片/特典/汉化版并存）；② 详情页要有**媒体沉浸感**（背景用游戏画板模糊，配音乐播放器、视频卡片、截图墙）；③ 竖版封面 + 横版画板是两种资源，不能混用。

### 共识的数据概念（游戏条目应有的属性）

中文名称 / 原名 / 简介 / 竖版封面 / 横版画板 / 安装目录 / 主可执行文件 / **其他可执行文件（列表）** / 添加时间 / 最近游玩 / 游玩时长 / 游玩次数 / **状态（正在游玩·已完成·待玩·暂停中·未玩过）** / 标签 / 角色。

## 3.2 元数据刮削（P1）

### 四源共识与优先级

| 优先级 | 来源 | 数据特点 | 用途 |
|---|---|---|---|
| 1 | **Bangumi**（bgm.tv） | 中文信息最全 | 中文名称、简介、标签 |
| 2 | **ymgal** | 中文 Galgame 站 | 补充中文信息 |
| 3 | **cngal** | 国内资讯站 | 国内游戏资讯 |

### 匹配策略共识（关键产品规则）

| 匹配率 | 处理方式 |
|---|---|
| **> 90%** | 自动采用（默认阈值 90%） |
| **70-90%** | 弹窗提示，用户确认（显示候选列表） |
| **< 70%** | 用户手动选择刮削源或自定义 |

### 字段级来源优先级（共识）

| 数据类型 | 优先来源 | 格式要求 |
|---|---|---|
| 游戏名称 | Bangumi 中文 > 原名 | 中文名称优先 |
| 游戏封面 | VNDB / Bangumi | **竖版海报式封面优先** |
| 游戏画板 | VNDB | **横版官方宣传图优先** |
| 游戏简介 | Bangumi | 中文描述优先 |
| 角色/标签 | VNDB + Bangumi | 合并数据 |

### 刮削流程共识（PRD 原文逻辑）

游戏添加 → 提取名称特征 → 调 Bangumi 搜索 → 计算匹配率 → 分支（自动/确认/手动）→ 获取详情（封面、简介、角色、标签）→ 存入本地库。

### 刮削的运行规则（后期共识，属于产品行为）

| 项 | 共识 |
|---|---|
| 匹配算法语义 | 100% = 完全匹配；90%+ = 包含匹配；**90%+ 自动接受阈值**（基于名称相似度） |
| **写库前必须预览** | 应用元数据前展示**合并预览**：列出"将变更的字段"与"不变的字段"（字段名、当前值、新值、是否标记保留）；用户可勾选**"保留我自定义的字段"** —— **先预览、后写入** |
| 单游戏刮削状态机（8 态） | 自动接受成功 / 成功但**待人工复核** / 无匹配 / 已完成而跳过 / 失败 / 排队中 / 处理中 / **用户取消** |
| 批量刮削 | 可多选游戏入队；后台执行、可停止、可取消；进度指标 = 总数 / 已完成（含失败）/ 成功数 / 失败数 / 跳过数（已有完整元数据）/ **待复核数** / 当前处理的游戏名 / 百分比 / 已用时长 / **预计剩余时长**；事件 = 进度变化 / 单个游戏完成 / 整批完成（含汇总） |
| 缓存策略 | **双层**：内存缓存 30 分钟 + 持久缓存（本地库，长期）；缓存键 = 数据源 + 清洗后的游戏名；失效条件 = 手动清除 / 数据更新 / 超时；**提供"清除缓存"入口** |
| 请求频率 | Bangumi 默认间隔 500ms；VNDB 默认间隔 200ms（共识建议用缓存降低请求） |
| 每次请求可追溯 | 结果必须携带"来源 + 实际搜索关键词 + 成功与否 + 错误信息" → **任何一次刮削失败都可解释给用户** |
| 兜底提示（共识原文） | 匹配不到时建议："用游戏原名（日语）搜索"、"检查数据源是否启用"、"手动搜索并选择最佳匹配"、"去 Bangumi/VNDB 网站手动找 ID" |
| Stub（占位）模式 | 三个开关（全局 / ymgal / cngal）**默认开启**，用途为四类："开发阶段"、"离线测试"、"速率限制规避"、"模拟异常场景测试错误处理" —— 即"功能先摆在那里、先不接真源"是**有意的产品决策**，不是疏忽 |

### 数据源扩展的产品约定（共识，重构时应保留）

任何新增数据源，必须走完这 6 步才算合规：
1. 独立请求通道 → 2. 独立响应模型 → 3. **产出统一元数据语义**（中文名 / 原名 / 简介 / 封面地址 / 多语言标题列表）→ 4. 注册来源枚举 → 5. 接入刮削编排（并行搜索）→ 6. 纳入缓存体系。

配套两条**契约**（属于产品体验承诺，不是技术细节）：
- **结果契约**：每次源查询都必须返回"来源 + 关键词 + 成功标志 + 错误信息"，**失败必须可解释，不允许静默失败**。
- **异常契约**：**用户取消不算错误**；其他异常一律降级为"带错误信息的失败结果"，**不允许崩溃**。

# 第六部分　共识：两个预留功能（P2，未来版本的核心）

> 这两个功能在 PRD 里"第一版只预留接口、前端隐藏"，但**讨论得非常细**，是本产品真正的长期价值所在。以下是完整产品规格。

## 6.1 流程图追踪（首创功能）

**产品目标（路线图措辞）**："流程图可视化展示"、"分支选择导航"。
**覆盖边界**：只覆盖部分游戏，不存在时返回"游戏不支持流程图"。

**查询维度**：按游戏 / 是否包含隐藏路线（默认 false）/ 语言（默认 zh-CN）。

**数据形态**：节点 + 连线 + 路线分组，节点带二维坐标，连线带颜色与虚实样式 → **目标是可视化路线图，不是文本攻略**。

| 概念 | 取值 / 属性 |
|---|---|
| **节点类型** | start 起始点 / route 路线节点 / branch 分支节点 / ending 结局节点 / event 特殊事件节点 |
| **选项（分支）** | 选项文本 + 跳转目标 + **解锁条件**（flag/value，如 `route_b_unlocked`） |
| **路线** | 名称、配色、包含的节点集合、**关联成就标识**（走完路线即解锁成就） |
| **结局** | 结局类型（good 等）、**关联 CG 列表** |
| **路线节点附加** | 所属角色、路线类型（如 romance） |
| **汇总元数据** | 路线总数、结局总数、通关预估时长（示例 20h）、流程图版本与最后更新 |

**产品含义**：流程图是**可演进的社区维护数据**（带版本号），不是一次写死的静态资源。

**接口共识**：`GET /api/v1/flowcharts/{game_id}`（获取结构）、`POST /api/v1/flowcharts/{game_id}/sync`（**把存档位置同步到流程图节点**——这是"存档节点标记"与"流程图"的咬合点，也是整个产品最巧妙的设计）。

## 6.2 社区成就系统

**类型（5）**：story 剧情成就 / normal 普通成就 / hidden 隐藏成就 / rare 稀有成就 / community 社区成就。

**单条成就属性**：名称、描述、**图标 + 独立未解锁图标**、类型、点数、进度（当前/总数/百分比，可为空）、是否解锁、解锁时间、**稀有度**（示例 0.15 / 0.01）、是否隐藏。
**社交保护**：隐藏成就在未解锁时名称与描述显示为 `???`。

**汇总**：成就总数、总点数、用户维度"已解锁数 / 已得点数 / 完成百分比"。

**上报机制**：客户端上报进度与元数据（含"已解锁 CG 列表"、最后解锁时间），服务端回传是否解锁 + **解锁通知**（标题"成就解锁！"，内容为成就名 + 图标 + 点数）。
**错误语义**：未登录 / 进度数据无效 / 成就已解锁 / 上报过于频繁。

**与流程图的耦合**：路线对象携带成就标识 → **走完一条路线 = 解锁对应成就**。

**你亲手定的两条实现路径**：**存档解析推断** + **进程内存监控**（后者对应设置里那个默认关闭的"内存行为监控（用于成就追踪）"开关）。

**接口共识**：`GET /api/v1/achievements/{game_id}`、`POST /api/v1/achievements/{game_id}/unlock`（上报）、`GET /api/v1/achievements/share/{id}`（生成分享卡片）。

## 6.3 两个功能的共同产品决策（共识）

- **以远程 API 服务为主**（你的判断 3），客户端只做展示与上报
- **以 Bangumi 条目 ID 作为跨系统主键**（例如 `bgm-12345`）——补丁、流程图、成就三个接口统一用它标识游戏
- 所有自定义 API 均需认证（API Key / JWT）
- 长期与 1.1.0"社区评论/推荐算法"、2.0.0"社区功能平台/开放 API"同属一条社区化路线
